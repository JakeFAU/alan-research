## Checker boundary and hostile tests

Current raw validation already handles immutable source/wire/reservation/debit, exact authority path/custody, ordinals, and fresh policy at fact prefix (`research/delegationcorrespondence/check.go:488–494,505–555,800–850`, `binding.go:36–99`). Reuse `CheckBindingRaw` on every declared cut and check that custody is declared. `binding_files.go:34–98` verifies digests and continuity, runs the current physical checker on final, and preserves old projection. `CheckExternal` validates original-level physical joins using final Store (`external.go:31–207`), reports retained gate ordinals and owner-local boundary facts separately (`:209–268`), and checks first-owner renewal (`:421–495`). Its acknowledged loss validation (`binding_files.go:102–149`) checks PID/signal/nonempty boundary/token and, for nonempty Subject, matches run coordinates. For this subjectless runtime ack it does not prove the exact `InFlight` authorization, endpoint ack identity or endpoint-commit-before-loss. Inline reopened capture is not a recognized `/post-open` owner record. Continuity checks append-only evidence (`external.go:274–355`), while `checkOwnerRenewal` (`:395–418`) is the starting point for stronger exact renewal verification with bidirectional run/table coverage.

Phase 3B.5 strengthens final endpoint artifact/coverage checks (`revocation.go:229–288`) and scopes out changed PID/acknowledged loss and external application without retained receipt (`:155–175,199–225`). `projectRevocationCapture` only includes final physical exposure at final or when an earlier local result already exists (`:380–383`). It requires epoch-1 source and one gate for the old live-owner relation (`:441,489–512,668,709`). Merely dropping those restrictions would smuggle later evidence into earlier cuts. Existing model Apply depends on a permit and is joined to a local receipt for old correspondence (`:503–535`). At model level it couples application with a durable result from which further service is enabled. `research/authorityservice/model.go:370–385` clears only the crashed server's permit, and `:414–423` disables dispatch-refuse if modeled as already Applied. Therefore neither an old atomic Apply at endpoint commit, nor setting Applied and inventing two agent crash transitions, establishes this concrete relation.

A smallest supportable new result is an opt-in split observation relation with separately retained original authorization/debit, a volatile admitted opportunity, an externally witnessed committed application, and a local result/custody state. A single owner-loss edge clears the volatile opportunity while preserving the world observation and retained attempt. Reopen records the exact current activation change. Revocation changes the selected root's eligibility; a refused fresh gate records only that new opportunity was denied, with no negative original-outcome assertion. Report whether world evidence was available by the cut under the pinned schedule or only appears later at dossier level. Keep the current raw, physical, continuity, process/cut attribution and model-support verdicts separately visible. If this slice remains a trace checker, do not call the result universal simulation or model-checked progress. If a new finite model is pursued, separate world-state mutation from receipt, model one shared owner loss explicitly, and allow post-loss fresh refusal on an unresolved original even when the world already applied.

Minimum adversarial checks, with coherent rehashing when useful:

- Admit or reserve only, then try to infer application from an allowed gate, final journal/snapshot, or claimed classification. N07 intermediate cuts and v1 06a distinguish these. Try to erase the genuine pre-loss positive world observation because the fresh gate refused.
- Missing endpoint acknowledgment with genuine final journal, wrong endpoint ack phase or pre-apply ack, mismatched key/auth/source/token/Store/PID, swapped endpoint ready records, missing committed line, mismatched receipt process or snapshot coverage. Require both corroboration and pre-loss causal link.
- Wrong Runtime ack scenario/PID, missing or different in-flight authorization, wrong wait status, a second loss declaration, false unchanged owner, or endpoint process conflated with the owner. A PID change or epoch bump alone is not acknowledged process loss. A consistent switch to a different producer protocol requires fresh evidence for temporal semantics.

Keep retained authorization unchanged in attacks against the fresh gate.

One application is compatible with multiple exposures, which must be rejected or excluded explicitly.
