### A restricted necessity lemma and proof

Fix a deployment with two static subjects, a parent and an unmodified child. Use the seven-instruction parent calculus over a ledger-only terminal boundary. Ordinary effects can send messages or call an endpoint whose responses depend only on its own state and requests. Only the environment can change another run’s lifecycle, and it issues no such command in this experiment. There are no invocation or host-query channels. A local translation can replace the parent program within this deployment. All grants, limits, endpoint state and public inputs agree.

Initialize one private child register to 0 or 1 before the parent starts. In the historical model a private startup receive can supply the bit. The child waits for the same work message, leaves that register untouched, branches on it, then immediately ends with the corresponding success or failure. It emits nothing. Each branch has the same enabled steps, admission windows, and resource debits. Give both terminal representations ample space and couple untimed service choices independently of the private bit. Compare the **named parent’s** emitted intents, blocked receives, and terminal status. The global journal already distinguishes the child’s two outcomes.

**Claim.** For every parent program in the seven-instruction core, the two runs have the same sets of finite parent-visible traces in this experiment. Consequently no such program can implement even the zero-retry policy that propagates the silent child’s success or failure.

1. **Base.** Pair configurations with equal parent artifact, projection (PC, data, status), run identity, epoch, sequence, available observations including payload and consumption state, and remaining limits. The private bit and any subsequent child terminal classification are outside this view.
2. **Local step.** Induct on the length of a paired execution prefix. `set` and `add` evaluate the same operands, including type, overflow, and size checks. `branch` and `jump` select the same PC. At `receive`, the same guard can select the same eligible envelope and bind the same fields, or both sides wait. At `emit`, the descriptor and updates agree, and the same run identity and sequence yield the same operation handle. `end` gives the same parent status. A matching commit therefore restores equality of the parent view. The reasoning applies in either direction, including identical limit failures. [Reducer and its complete input boundary](https://github.com/JakeFAU/alan/blob/c6f9df6707deb90b0704551c71b5231da2ab5838/internal/executor/program.go#L292-L488)
3. **World step.** Terminal delivery changes only a hidden ledger. A message probe to the child sees the same open/closed and generation checks, even if its admission receipt is exposed. If the parent withholds work, both children remain waiting. If it supplies work, pair the receive, branch and End steps at the same cuts. Other ordinary sends and endpoint calls have identical descriptors, public state, and responses. Thus every permitted input, refusal, and scheduling choice in one run has a counterpart in the other. In the pre-1C model these checks appear in admission, receipt recording, and ledger-only delivery. Its additional local frontier operations likewise depend only on local state. Even a *blind* retry would need separate treatment. Creating a successor on only one side could change the response to a later message probe. [Historical world and reducer at `82dc5649`](https://github.com/JakeFAU/alan/blob/82dc5649cfe0eccb2fde3ecea1e12cc851377af5/research/semantics/model_test.go#L365-L618)

Under a schedule that services the specified supervisor, the source admits a finite parent-success observation for the successful child. Parent success is impossible in the failed-child case at zero budget. The same translated parent must handle both private inputs. With identical possible parent traces it must either lose the successful trace or allow it in the failed case. Permanent waiting cannot supply the missing finite trace. The argument requires only the existence of the serviced source execution.

There is a separate **authority requirement** for a positive retry budget. At the historical boundary, only the environment’s `retry` transition advances the child generation. With no intervening operator, induction on ordinary commits, deliveries and effects leaves that generation unchanged. A parent required to create generation 2 after a retryable failure cannot do so there. Now suppose the parent *can* request a retry. If acceptance and refusal are both possible from the same parent view, the prescribed next actions differ again. Sending successor work in the refusal case adds an observable intent, while escalating in the acceptance case omits that work. The policy needs access to the committed decision or an equivalent correlated signal. An authenticated service with a correlated reply is one possible boundary. No particular tag spelling follows from either argument. ## 2. Which evidence can be combined?
