## Transport reduction correction

The thirteen-phase proposal above is a global delivery-schedule restriction. In the original rules a server can fill an empty result slot while the caller holds an earlier volatile copy. Removing that transition using the caller's volatile or durable receipt in an application-side guard would give the server undeclared remote-state knowledge. Prefer retaining server-local result-slot eligibility and explicitly declaring any restricted event alphabet.

With all originals seeded committed/admitted, the original Phase 3B.1 edge guards, and one receipt value, a state-space ceiling is available without a run. Per edge the request slot contributes a factor of two. Before Apply there is one local phase. Applied/unrecorded has a retained receipt and four combinations of result slot and volatile caller copy when up, two when down. Recorded has independent retained, ACK, consumed and result slot bits. Its volatile copy is present when the caller never crashed, absent when down, and may be absent or present after recovery. Thus the local per-caller-phase ceilings are 42 (original-up), 38 (down), and 74 (recovered-up), giving 71,148 chain states and 3,652,264 cycle states per profile. They are ceilings, not exact reachable counts. Fixing the admitted cut and excluding further request sends/dedup as a declared schedule restriction fixes that request slot empty and gives 17,787 chain and 456,533 cycle states per profile, while preserving the complete result/ACK transition rules including the callee's resend.

A cheaper, protocol-defensible subgraph also restricts result delivery to the original retained-copy variant (ReceiveResult with Duplicate=true). One can interpret it as a persistent one-slot mailbox read by the caller. The callee can send whenever its retained receipt exists and that slot is empty. On caller loss the volatile copy clears, and the surviving mailbox allows a reread even after callee release. This uses the original local guards and chooses a fixed event variant, with no caller-state test at the server. Under this choice the result slot stays occupied once filled. Before Apply there is one state, Applied/unrecorded contributes three states if up and two if down, and Recorded contributes eight when originally up or down and sixteen when recovered. Local bounds are 12/11/20. With request slots fixed empty the corresponding ceilings are 5,547 and 79,507 per profile. If retaining request send/dedup as in Phase 3B.1, the bounds become 22,188 chain and 636,056 cycle. The mailbox restriction leaves transport undrained on completed prefixes and qualifies the explicitly selected subgraph. If draining or full duplicate behavior matters, use the unrestricted result/ACK variant, cap the profile matrix if necessary, and stream one graph at a time.

A bounded completion argument can use the pending service dependency graph. Its vertices are the frozen originals that remain unapplied. Draw an arc from incoming original e to the serial server's outgoing original f only if f is still unapplied and blocks e; if f is already applied, route and record its authentic receipt, or consume its existing durable record, before checking the next application. After permitted recoveries, any finite acyclic dependency graph has an unapplied vertex with no pending predecessor requirement; schedule that application and its custody chain, then reduce the number of unapplied originals. In the named chain and cycle, one servicing server removes its incoming application's wait dependency. This argument needs the specific fact that applied originals always have a route to consumption under the chosen channel restriction and honest eventual handling. Compatibility of message shapes alone does not discharge the service rely. Treat compatibility of safety premises, discharge of progress premises, and equivalence under grouping as separate checked claims. For an all-serial seeded cycle the conditional progress premises are mutually unsatisfied from the outset; transport duplicates or recovery loops do not witness a first application.
